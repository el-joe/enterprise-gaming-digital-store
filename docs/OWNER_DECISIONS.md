# Owner decisions

These are binding product decisions from the owner. Each one says where it is built. Newer entries go at the bottom.

## 2026-11-10: answers to the M-A8 design questions

| # | Question | Owner answer | Decision as built | Where |
|---|---|---|---|---|
| 1 | Currency shown and charged | Show each user prices in their country's currency; charge in the gateway currency: **Paymob charges EGP, every other gateway charges USD**. | **Display (owner restated 2026-11-10: "while browsing he must see prices in his country pricing"):** every page that shows a price (home, listings, search, product, cart, checkout, emails and the app) shows it in the customer's country currency. The country is taken from the signed-in customer's profile country, else GeoIP. The currency is that country's currency only if it is active with a fresh rate, otherwise USD. A saved choice (cookie, profile, `X-Currency`) always wins, and the switcher stays available. **Payment:** fixed per gateway. Paymob always charges EGP and Stripe, PayPal and the wallet charge USD. The `charge_display_currency_only` restriction on Paymob is removed, and Paymob is offered for any display currency, still subject to country and eligibility rules. Checkout shows the display amount and the exact charged amount ("You will be charged E£… / $…"). Conversion uses the existing rate snapshot and margin floor, once per order. | Backend change "OD-1", run after M12; web checkout (M12 or M13); app checkout (M-A13) |
| 2 | Digits in Arabic | Keep Western digits (123). | As designed: Latin digits everywhere, with left-to-right marks around amounts in RTL text. | Web and app |
| 3 | Store policy blocks in-app purchase | Send the user to the website. | Build a "Complete purchase on boxcards.shop" state behind a remote flag in `/app/config`. It opens the product or cart on the web in the system browser, and is enabled only if store review requires it. | Backend app config flag (OD-1), app (M-A13) |
| 4 | Guest checkout | Must log in to check out. | **App:** no guest checkout. Checkout starts by signing in or registering, and the cart is kept and merged on login. **Web:** the same; the owner confirmed on 2026-11-10 that the website also requires login. Guest checkout is off on both, behind a single setting (default off). Guest order access by email and OTP stays only for any existing guest orders. | App (M-A13), web (M12) |
| 5 | Rooted or jailbroken devices | PM decides. | **Warn, don't block.** A one-time warning sheet appears on rooted or jailbroken devices. Code reveal stays allowed but always requires recent password or biometric confirmation, and a device-integrity flag is sent with reveal requests and stored in the reveal audit log so the risk engine can act. Screen-capture protection is on for code screens. Reason: many gamers root their devices, and blocking would lose legitimate buyers, while the server-side audit, rate limits and re-auth protect the codes. | App (M-A14), backend audit field (OD-1) |
| 6 | Biometric unlock | Yes. | Optional fingerprint or Face ID. It is offered after the first login and can be turned off in Security settings. It unlocks the app after 5 minutes in the background, and on a supported device it can satisfy the code-reveal re-auth (via the stored refresh credential, never by storing the password). If biometrics change, it falls back to the password. | App (M-A10, M-A16) |
| 7 | Code auto-hide | Follow market practice. | Gift-card stores keep codes viewable in the account and mask them by default. Password managers hide on background and clear the clipboard after about 60–90 seconds. Built: codes are masked by default; **auto-hide after 60 seconds**, and immediately when the app goes to the background or the screen is left; content is blurred in the app switcher; **the clipboard is cleared after 60 seconds**; screenshots are blocked on Android and the content is hidden during capture on iOS. | App (M-A14); web reveal (M13): mask, auto-hide after 60 seconds, hide on tab switch |
| 8 | Home banner | Follow market practice. | **Auto-advance every 5 seconds**, with a pause on touch, swipe or focus. It doesn't resume while the user interacts, stops when off-screen, and doesn't auto-advance when the OS "reduce motion" setting is on. Web: a visible pause/play button (WCAG 2.2.2) and page indicators. | Web (M12), app (M-A11) |

## 2026-11-11: push notifications provider

| # | Question | Owner answer | Decision as built | Where |
|---|---|---|---|---|
| 9 | Push provider for the app (roadmap open decision 3) | Use Firebase Cloud Messaging (FCM). | FCM for Android, and for iOS through APNs (FCM relays to Apple's service). The backend gets device registration, a `push` channel in the notification preferences, and sends for order delivered, payment failed and ticket reply. Payloads carry ids and short text only: never codes, secrets or amounts beyond what the inbox shows. The app asks for permission after the first purchase, registers and refreshes the token, and opens the order or ticket on tap. Until the owner creates a Firebase project and supplies `google-services.json` / `GoogleService-Info.plist` and the server credentials, sending is faked in tests and switched off by configuration. | M-A18 (backend and app) |

## 2026-11-12: settings from the database

| # | Question | Owner answer | Decision as built | Where |
|---|---|---|---|---|
| 10 | Where the project's own configuration lives | "Change all new variables in .env to be changed from the database instead." | Every `.env` key this project added (payment return URLs, Open Exchange Rates app id, GeoIP, MCP limits, n8n outbox and secrets, account email links, app links and biometric lifetime, mobile web checkout and forgot-password links, FCM, guest checkout, admin theme and idle timeout, blocking crawlers) is an admin setting edited in Admin > Settings, applied over config at boot and in workers. Secrets are encrypted with `APP_KEY` and write-only; the FCM service-account JSON is uploaded instead of a key file path. Security-sensitive groups need `settings.manage_critical`. Kept in `.env`: the code-vault keys (`DIGITAL_CODE_*`: next to the ciphertext they would defeat the encryption), `SUPER_ADMIN_*` (bootstrap the first admin), `STRIPE_API_VERSION` (code-coupled), `SEO_SITEMAP_DISK` (infrastructure) and the Laravel framework keys. Existing values are copied once with `php artisan settings:import-env`; the owner then removes the lines from `.env`. (Superseded in part by decision 11: the code-vault keys, `STRIPE_API_VERSION`, `SEO_SITEMAP_DISK` and the framework keys moved too.) | Backend ("Settings from the database" in `PROGRESS.md`; `DEPLOYMENT.md` 3.1 and 3.2) |
| 11 | What may stay in `.env` | "Don't leave anything in .env except the super admin." | Only the Super Admin and technical bootstrap keys stay in `.env`: `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD` (owner's choice), `APP_KEY` and `APP_PREVIOUS_KEYS` (they decrypt every encrypted setting), `APP_ENV`, `APP_DEBUG`, `DB_*`, the cache, session-store, queue, Redis, Memcached and broadcast infrastructure, `LOG_*`, `APP_MAINTENANCE_*`, `BCRYPT_ROUNDS` and `VITE_APP_NAME` (compiled into the frontend). Everything else is an admin setting applied over config: the store name, address and languages, sessions, mail (SMTP password encrypted), files and S3 (secret encrypted), token lifetimes, timeouts, the Stripe API version (read-only, pinned in code), the sitemap disk, and the gift-code vault keys. The vault keys are envelope-encrypted with `APP_KEY`, never shown or edited in the admin (only their state, active key id and count), changed only by `codes:generate-keys`, `codes:rotate-key` and `codes:rebuild-blind-index`, imported byte for byte so existing codes still decrypt, and audited with a security event. A test fails if a config file reads any other key from the environment. | Backend ("Only bootstrap keys in .env" in `PROGRESS.md`; `DEPLOYMENT.md` 3.1 to 3.3; `SECURITY.md` 5) |

## 2026-11-12: supplier images

| # | Question | Owner answer | Decision as built | Where |
|---|---|---|---|---|
| 12 | Product images from the supplier catalog | "Sync the supplier catalog with images, replace the card background with the available image, and the synced image must be optimized and converted to AVIF." **Overrides BD8 for supplier-provided product images** (Reloadly `logoUrls` and `brand.logoUrl`). The owner is responsible for the rights under the reseller agreement. | The catalog sync queues one `FetchSupplierProductImage` job (`sync` queue) per product whose image URL is new or changed. The product's own card image (`logoUrls[0]`) is preferred over the brand logo. Download rules: HTTPS only, host on `suppliers.image_hosts` (`cdn.reloadly.com`, the only host in the synced data), no redirects, 10 s timeout, 5 MB, an `image/*` type that is not SVG, decoded and re-encoded with GD. Stored as AVIF (quality 50) and WebP at 960 and 480 px wide (no upscaling) under `media/supplier-products/{id}/`, deduplicated by source URL and SHA-256. "Add to store" makes it the product's primary image; products added earlier get it when it arrives, unless a staff image exists. A staff image always wins and is never replaced. The storefront card, product page and listing draw it as the tile background (`<picture>`, AVIF then WebP), with the generated art as the fallback. Owner request on the same day: admin image fields are file uploads (`<x-admin.image-upload>`) through the same optimizer, not media id numbers. | Backend ("Supplier images" in `PROGRESS.md`; `ASSETS.md`) |
